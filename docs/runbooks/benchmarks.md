# Benchmarks — runbook

**Design**: `docs/superpowers/specs/2026-09-05-benchmark-suite-design.md` ·
**Contract**: `docs/superpowers/plans/2026-09-05-benchmark-suite.md` ·
**Runner**: `scripts/bench/`

A *test* answers "does this still work?". A *benchmark* answers "how well does
this work, and is it getting better or worse?" — it produces a number, compares
it against a committed baseline and a floor, and is run the same way every time
so the number means something across weeks.

---

## Commands

| Command | What it does |
|---|---|
| `npm run bench -- --list` | every suite, its tier, its `requires`, and whether this machine can run it |
| `npm run bench -- --suite=<name>` | run one suite, write its result, print the table |
| `npm run bench -- --suite=<name> --compare` | …and fail (exit 1) if a gate/nightly metric crossed its floor |
| `npm run bench -- --tier=gate --compare` | every gate-tier suite whose `requires` are met — what CI runs |
| `npm run bench -- --suite=<name> --json` | results as JSON on stdout (human output moves to stderr) |
| `npm run bench -- --suite=<name> --update-baseline --reason="…"` | rewrite that suite's baseline rows; refused without `--reason` |
| `npm run bench:compare` | re-read `reports/benchmarks/latest/` against the baseline without re-running anything |
| `npm run bench:validate` | the five-part check on every suite config (also runs inside `pipelines:validate`) |
| `npm run bench:test` | the runner's own unit tests |
| `node scripts/bench/suites/<name>.mjs --self-test` | run one scorer standalone, no runner involved |

The `bench` script runs under `node --import tsx`, so a scorer may import
production TypeScript directly.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | everything passed, watched or was skipped — and **every** run without `--compare`, which measures rather than judges |
| 1 | with `--compare`: a **gate**- or **nightly**-tier metric under its floor, or a suite whose scorer threw |
| 2 | a usage or config error — unknown suite or tier, unparseable config, `--update-baseline` without `--reason` |

**Tier decides the consequence; status decides the meaning.** A `watch`-tier
suite can record `FAIL` in its result file and its table row — that is the
point of the tier — without failing the run. Only `gate` and `nightly` failures
change the exit code.

## Adding a suite: the five parts

A benchmark that is missing any of these is not accepted (design §3), and
`bench:validate` enforces the four that can be checked statically.

### 1. Fixture — `config/benchmarks/fixtures/<suite>.json`

The corpus. Labelled by a human where the label is a judgement ("a good
match", "a must-detect crisis line"), generated where it is mechanical. **No
real student data, ever** — the synthetic cohort lives in
`config/benchmarks/synthetic-cohort/` and is generated by
`scripts/bench/seed-cohort.ts`.

A suite that measures the repository or a seeded database rather than a
committed corpus (coverage, migration drift, cron health) may declare no
`fixture`; `bench:validate` prints a note rather than an error. A declared
fixture that does not exist **is** an error.

### 2. Scorer — `scripts/bench/suites/<suite>.mjs`

```js
import { fit } from "../../../src/lib/connect/matching.ts"; // import production code
import { selfTest } from "../lib/self-test.mjs";

export async function run(ctx) {
  return { metrics: [{ id: "precision_at_3", value: 0.83, n: 30, details: { missed: [] } }] };
}

await selfTest(import.meta.url, run); // inert unless run directly with --self-test
```

- Deterministic where possible. A model judge may only feed a metric whose
  suite tier is `watch` — never a gate.
- **Import production code; never copy prompts or logic into the fixture**, or
  the benchmark measures a copy that cannot drift with the app.
- `details` is free-form evidence (which cases missed, which offenders) — and
  is written to a committed result file, so it must never contain student data.
- Return one entry per declared metric. A declared metric the scorer does not
  return is an `error`, not a silent pass; an undeclared metric is dropped with
  a warning.
- Optionally return `provider` and `model` alongside `metrics` — they land in
  the result and the baseline row.

The `ctx` handed to `run`:

| Key | Value |
|---|---|
| `fixture` | the parsed fixture JSON, or `null` when the suite declares none (or a non-JSON path) |
| `fixturePath` | absolute path to the fixture, or `null` |
| `env` | `{ databaseUrl, geminiApiKey, ollamaHost, baseUrl, prodReadonlyUrl, playwright }` — every value a string or `null`, never `undefined` |
| `log` | `(...args) => void`, prefixed with the suite name |
| `now` | `() => Date` |
| `suite`, `config` | the suite name and its parsed config |
| `repoRoot`, `commit`, `host` | the checkout, the short SHA (or `null`), and the host block |

The first six are the shared contract; the rest are additive conveniences.

### 3. Baseline — `reports/benchmarks/baseline.json`

One row per metric, written only by `--update-baseline` (below).

### 4. Floor and tolerance — in the config, never in the runner

```json
{ "id": "recall_must_detect", "unit": "ratio", "direction": "higher", "floor": 0.98, "tolerance": 0.01 }
```

- `unit`: `ratio` (0–1) · `percent` (0–100) · `count` · `ms` · `grade` · `seconds`
- `displayUnit` *(optional)*: a free-form label — `"usd"`, `"students/week"` —
  carried through to the result and the dashboard **untouched**. `unit` stays
  the enum, because that is what every reader formats a value by; a display
  label never changes how a number is judged.
- `direction`: which way is better. `floor` is read in the metric's own
  direction — a `lower` metric must stay **≤** its floor.
- `tolerance`: the absolute drop from baseline that opens a `watch`.
- `"exact": true`: the value must equal the baseline. `direction` may be
  omitted for an exact metric; `floor` and `tolerance` are ignored for it.

#### A gate metric with no floor yet

Some numbers must be recorded before anyone can say what "good" is — cost per
student before Britt sets a budget, for instance. A `gate`- or `nightly`-tier
metric may skip its floor **only** by saying so out loud:

```json
{ "id": "cost_per_student_month", "unit": "count", "displayUnit": "usd",
  "direction": "lower", "floor": null,
  "reason": "budget is an owner decision (design §9.4); recorded until one is set" }
```

`"floor": null` plus a non-empty `"reason"` makes an owner-documented `info`
metric: it is measured, written, and shown, and it never gates. Anything less
is an error — a **missing** `floor` key is an omission, an explicit `null` is a
decision, and the validator treats them differently on purpose. On the `watch`
and `manual` tiers no reason is needed, because nothing was ever gating there.

### 5. Tier — in the config

| Tier | Runs | Consequence |
|---|---|---|
| `gate` | every PR (`ci.yml`) | a floor breach fails the PR |
| `watch` | every PR and nightly | reported, never fails |
| `nightly` | `benchmarks.yml` | a floor breach fails the nightly and opens the regression issue |
| `manual` | by hand | recorded in an artifact |

Gate- and nightly-tier metrics must carry a `floor`, `"exact": true`, or an
explicit `"floor": null` with a `"reason"` (above) — a gate with nothing to
cross is not a gate, and `bench:validate` says so.

### `requires`

`postgres` · `cohort` · `gemini` · `ollama` · `browser` · `prod-readonly` ·
`server`. The runner maps each to an environment variable —
`DATABASE_URL` (for both `postgres` and `cohort`), `GEMINI_API_KEY`,
`OLLAMA_HOST`, `PLAYWRIGHT`, `BENCH_PROD_READONLY_URL`, `BENCH_BASE_URL` — and
marks the suite **`skipped`** when one is unset. Skipped is never a failure:
the missing secrets are owner steps, and a benchmark that reds a PR because a
key was never set teaches everyone to ignore the gate.

## Reading a result

`reports/benchmarks/latest/<suite>.json`, schema
`config/benchmarks/result.schema.json`:

```json
{ "suite": "crisis-en", "tier": "gate", "startedAt": "…", "durationMs": 1234, "commit": "abc1234",
  "provider": null, "model": null, "host": { "os": "…", "cpus": 4, "memGb": 16, "node": "v24", "ollama": null },
  "metrics": [ { "id": "recall_must_detect", "value": 0.985, "unit": "ratio", "n": 200,
                 "floor": 0.98, "baseline": 0.99, "status": "pass" } ],
  "status": "pass" }
```

Statuses:

| Status | Meaning |
|---|---|
| `pass` | inside the floor and inside the tolerance |
| `watch` | below `baseline − tolerance` (above `baseline + tolerance` for a `lower` metric) but still inside the floor |
| `fail` | the floor was crossed, or an `exact` metric moved |
| `info` | nothing to judge against — no floor and no baseline |
| `skipped` | no value: the suite's `requires` were unmet |
| `error` | the scorer threw, or did not return a declared metric |

The suite's own `status` is the worst of its metrics, except `skipped` and
`error`, which are facts about the run rather than about any metric.

## Updating a baseline

```bash
npm run bench -- --suite=crisis-en --update-baseline --reason="new ES corpus, 150 rows added"
```

The runner **refuses without `--reason`**. The reason is written into the
baseline row beside the value, the commit, the timestamp, the provider, the
model and the host fingerprint — so a moved number carries its own explanation
in the diff. A baseline that moves silently is how a floor quietly stops
meaning anything, which is the failure mode this whole suite exists to prevent.

**Floors extend, never relax** (PR #137's frozen-grader rule). Raising a floor
belongs in a PR that shows the new value being met. *Lowering* a floor needs an
owner decision recorded in the suite's config `notes`.

## The rules this suite inherits

- **Flake protocol** (2026-07-21). A gate-tier benchmark that fails is re-run
  **at most once**; a second failure is real. A scenario that flips at
  temperature 0 is demoted to `watch` *visibly*, never deleted.
- **Record the host.** Any local-model number without the machine behind it is
  rejected: a suite whose `requires` includes `ollama` must declare
  `"host": "recorded"` at the top level of its config, or already carry a host
  in its baseline row, and `bench:validate` fails it otherwise. Every result carries the host block, and
  every baseline row carries the one-line fingerprint. This rule exists because
  every local-model number in this repo's history has an unrecorded host, which
  is why they contradict each other.
- **Evict between arms** for any local A/B (2026-07-27): Ollama keeps every
  model it has served resident, so a large model starves the next one and its
  calls die at the provider timeout, looking exactly like a bad score.
  `curl -s localhost:11434/api/chat -d '{"model":"<m>","messages":[],"keep_alive":0}'`
- **No PII in fixtures or in `details`.** Result files are committed.
- **A number nobody reads is not a benchmark.** Every nightly result is
  uploaded and, on `main`, committed; every regression opens or updates the one
  issue titled "Benchmark regression".

## CI wiring

`ci.yml` (`verify` job), after the unit tests:

1. `npm run platform:validate` — the route/tool map check that, until now, ran
   in no workflow at all.
2. `npm run bench:validate` — the five-part check (also inside
   `pipelines:validate`; the explicit step names the failing gate in the log).
3. `npm run bench:test` — the runner's own unit tests. They live at
   `scripts/bench/__tests__/*.test.mjs`, outside `npm test`'s
   `src/**/*.test.ts` glob, so they need their own step.
4. `npx tsx scripts/bench/seed-cohort.ts` when that file exists, then
   `npm run bench -- --tier=gate --compare`, both pointed at the hermetic
   pgvector service so `postgres`/`cohort` suites meet a real migrated schema.

`benchmarks.yml`: nightly at 06:00 UTC plus `workflow_dispatch`. Same service,
migrations applied, cohort seeded, then `--tier=nightly --compare` followed by
`--tier=watch`. Uploads `reports/benchmarks/latest/`, commits it on `main` with
`[skip ci]`, and opens or updates the "Benchmark regression" issue on any
failure.

Suites needing `GEMINI_API_KEY` never run per-PR — only nightly, and only when
the secret exists (nightly Gemini spend is an owner decision, design §9.4).

## Owner steps

These are the secrets the suite reports `skipped` for until they exist
(design §9.7):

- `CRON_CHECK_DATABASE_URL` — the scheduled-layer health suite.
- `BENCH_PROD_READONLY_URL` — a read-only production connection string for
  drift, cost-per-student and FERPA-routing suites.
- `GEMINI_API_KEY` in the repository's secrets — the model-backed nightly
  suites. Confirm a monthly ceiling first (the 2026-08-21 credit-drain
  incident).
