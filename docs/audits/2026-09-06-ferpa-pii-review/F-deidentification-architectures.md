# De-identification / PII-shielding architectures for a cloud LLM in front of student PII
Research date: 2026-09-06. Context: VisionQuest (Next.js/TS, Prisma/Postgres+RLS), 100–500 adult TANF/SNAP students, wants a fast cloud LLM (Gemini today) without exposing PII, currently routes `student_record` data to a local Ollama model per FERPA policy (see `.claude/rules/sage-ai.md`).

**Cross-cutting finding on accuracy**: every generic NER-based detector (Presidio, spaCy, GLiNER, cloud APIs) has a documented failure mode on exactly what VisionQuest's chat log domain contains — first-name-only mentions, nicknames, lowercase casual text, and misspellings. The 2026 academic literature (`arxiv 2609.03464` "Mind the Gap: Robustness Risks in PII Detection Systems", `arxiv 2606.19881` "REDACT" benchmark) confirms this is a known, unsolved problem class, not something any vendor has fully cracked. No detector found in this search reports a benchmarked precision/recall specifically on "casual chat with nicknames and misspellings" — that gap has to be assumed and tested in-repo, not taken on vendor faith.

## 2. Structured substitution (VisionQuest already knows the identifiers)

Because VisionQuest's DB already holds each student's true name/email/phone/address/DOB, **the hard part of open-vocabulary NER is not needed for the identifiers the schema knows about** — this reduces to deterministic find-and-replace of a known small dictionary per request (student's own name/nickname variants, DOB, phone, address, email) plus a much narrower NER problem for the identifiers the schema does *not* know (a mentioned family member's name, an employer's name, a friend's phone number).

**Pattern, as published in industry sources** (Wavect's PII-redaction pipeline writeup, Skyflow's vault pattern, the "5 key anonymization techniques" piece from Redgate): build the request-time substitution map from the DB row for the acting student (`name → "Student"`, or a stable per-session token like `"[STUDENT]"`), run a lightweight NER pass over the free-text chat body for anything *not* already known (to catch family/employer/other-phone mentions), assign each newly-found entity a stable placeholder for the session (`"[FAMILY_1]"`, `"[EMPLOYER_1]"`), send the substituted text to the cloud LLM, then reverse the map over the streamed/completed response before it reaches the student.

**Published pitfalls, consistent across sources found**:
- **Placeholders measurably change model output, not just cosmetically.** The strongest evidence found: a controlled comparison from academic work on LLM confidential-data handling shows `[REDACTED]` produces qualitatively worse/different reasoning than a typed placeholder carrying light metadata (e.g., `<PERSON_1: female, 34>`) — the model reasons worse over a bare token than over one that still carries the grammatical/semantic role of a name. This argues for typed, role-preserving placeholders ("the Student", "the Student's employer") over opaque tokens like `[PII_1]`.
- **NER models — and by extension LLMs reasoning over redacted text — trained/tuned on natural text generalize poorly to placeholder-dense text**; perplexity/attention patterns skew toward the placeholder tokens themselves. A prompt that is 20% `[PLACEHOLDER]` tokens is out-of-distribution relative to what the model was trained on, which can degrade coaching-quality output, not just factual accuracy.
- **Partial matches and possessives are the most-cited implementation bug class**: naive string replacement on "Maria" will also corrupt "Mariana," and will not catch "Maria's" unless the substitution logic explicitly handles the possessive `'s`/`'` boundary — a bug class directly analogous to the `explain_job` substring-matching bug VisionQuest already found and fixed in its credential-matching code (word-boundary anchoring, not naive substring/prefix matching).
- **Streaming token boundaries are a real hazard for the reverse direction**: if the LLM's response is streamed to the browser via SSE (as VisionQuest already does for Sage), a placeholder token like `[STUDENT]` can be split across two SSE chunks by the provider's tokenizer, so a substring-based de-substitution running chunk-by-chunk can miss it. The safe pattern (implied across every reversible-tokenization source, and consistent with how Skyflow describes its own detokenize-on-return step) is to buffer a small trailing window of the stream (enough to hold the longest placeholder token) rather than doing string replacement independently per chunk — the same "you can't process a stream naively when your marker can straddle a boundary" problem VisionQuest's own `sanitizeForPrompt` fixpoint-normalization work already solved for prompt-injection markers, and the identical discipline should be reused here.
- **The model addressing the user by placeholder is a documented UX failure**, not just theoretical: if the system prompt says "the user's name is [STUDENT]," the model may literally say "Hello [STUDENT]!" back if the placeholder isn't stripped from the *reply* before final substitution, or may over-formalize ("Dear Student,") because the token reads to it as a title rather than a name. This argues for choosing a placeholder that is grammatically a plausible first name in isolation (a fixed generic first name, or the literal word "Student" used as a vocative) rather than a bracketed token, specifically for the parts of the prompt the model must "speak to."
- **Tool-call arguments are a distinct leak surface no source treats as solved**: if Sage's agent tools (as VisionQuest's already does with `propose_resume_edit`, `search_jobs`, etc.) take structured arguments, a placeholder substituted into free text does not automatically propagate into a tool's JSON arguments if the model independently reconstructs or infers the argument value — e.g., the model could still emit `{"studentName": "Maria Gonzalez"}` in a tool call even though "Maria" was replaced with "[STUDENT]" in the visible chat, if the model has residual context (session history, a RAG chunk) that still contains the real name. Every tool-call boundary is therefore a second de-identification checkpoint, not a place the substitution can be assumed to have already taken effect — this matches VisionQuest's existing architecture note that `SageOperation`/confirm-card payloads are separately audited, so the natural fix is to run the same redaction check on tool-call arguments before they're logged/executed, not just on the chat turn.
- **No source found evidence that redaction improves latency or cost meaningfully** — it's a pure privacy/quality tradeoff, and every source that measured quality found some degradation versus sending clean text, the size of which depends on how good the placeholder scheme is.

## 3. Data privacy vault / split-knowledge architecture, mapped to Postgres + RLS

Skyflow's architecture is the clearest published reference: identity data (name, email, phone, address, DOB) lives in one isolated store the app almost never queries directly for AI purposes; everything else (chat transcripts, goals, progress) is keyed by an opaque, non-reversible-without-the-vault token. Two ways to map this onto VisionQuest's existing Postgres+RLS setup, in increasing order of architectural change:

- **Cheapest, no new infrastructure**: treat the *existing* `Student.id` (a cuid, already opaque and already the RLS scoping key everywhere) as the "opaque token." The **only** new piece needed is a lookup table (or reuse of the existing `Student` row, gated behind a *stricter* RLS policy / a role that only the redaction layer can query) mapping `Student.id → {name, email, phone, address, dob}`. Direct identifiers already live in one place (`Student` model) rather than scattered — which is a real advantage VisionQuest already has over a green-field app. The work is: (a) never let those five columns reach the LLM prompt directly (enforce this the same way `resolveAiProvider` already enforces cloud/local routing — a lint rule or a Zod-validated prompt-builder that refuses to interpolate raw `Student.name` etc.), and (b) make sure chat's free-text NER-detected identifiers get the same non-reversible-to-cloud treatment.
- **Closer to Skyflow's actual pattern**: physically separate the identity columns into their own table/schema with RLS policies distinct from (stricter than) the behavioral tables (`Message`, `Goal`, `SpokesRecord`, etc.), so that even a compromised app-role credential that can read `Message` rows cannot also read `StudentIdentity` rows without a second, narrower-scoped role. This is a real Postgres RLS pattern (separate role + separate `GRANT`s, exactly the `vq_app` vs `prismaAdmin` split VisionQuest already runs for its admin/crisis path) rather than a new product to buy — it does not require an actual third-party vault vendor, only discipline in schema/role design.
- **A literal third-party vault (Skyflow etc.)** is the "buy" version of the same idea: it's justified mainly when you need vendor-attested compliance posture (SOC2/HIPAA-grade vault, PCI-style tokenization) or multi-tenant/cross-org sharing controls beyond what a single Postgres instance's RLS gives you. For a single-tenant, 100–500-student app already built on Postgres RLS, this is very likely **not worth the cost and integration overhead** — the RLS-based split above gets ~80% of the security property for near-zero marginal spend.

## 5. What de-identification does NOT achieve legally, and the recommended combination

**The core legal/practical limit, confirmed across NIST and FERPA guidance found**: de-identification (even done well) removes the *association* between data and a named individual, but it does not guarantee the data cannot be **re-linked**. NIST SP 800-188 frames de-identification explicitly around managing *disclosure risk*, not eliminating it — the standard talks about choosing a release model and evaluating "quasi-identifier" combinations that could re-singularize someone when cross-referenced against outside data. The re-identification literature found in this search (JAMIA 2026, the "k-anonymity & disclosure risk" material) confirms the mechanism directly relevant here: **a small, closed population is the worst case for de-identification** — 100–500 students in one West Virginia workforce program is a small enough population that a handful of quasi-identifiers surviving in a "de-identified" chat transcript (a specific employer name + a specific city + a specific certification path + an approximate age) can be enough to single someone out, even with the primary name/email/phone/DOB redacted. This is exactly the property NIST's framework calls out: risk scales with how many quasi-identifiers remain and how linkable the surrounding context is, not with whether the four or five "obvious" identifiers were stripped.

ED PTAC's own FERPA de-identification guidance (`studentprivacy.ed.gov`, "Data De-identification: An Overview of Basic Terms") makes the same point for the education-specific legal context: FERPA permits use of properly de-identified data, but the burden is on the institution to have a *defensible methodology*, not just to have run a redaction tool — a vendor's redaction pass is evidence toward that methodology, not a substitute for it.

**The combination practitioners converge on, and the one to recommend here**: **contract + minimization + redaction**, in that order of actual risk reduction — not redaction alone:
1. **Contract first** — a signed Data Processing Agreement / Business Associate-style agreement with the cloud LLM vendor establishing zero data retention and no-training terms is the single highest-leverage, lowest-engineering-cost step, and is a prerequisite regardless of which technical option is chosen (this is true even if VisionQuest also builds redaction — redaction reduces exposure on a given request, it doesn't replace the need for a contractual backstop covering the exposure that leaks through it).
2. **Minimization second** — send the LLM only what the specific turn's task actually needs (VisionQuest's existing `AiTask`-scoped provider routing is already a minimization mechanism; extending "does this task need the student's real name at all" as a per-tool question is free, structural minimization that beats any NER model's recall).
3. **Redaction/pseudonymization third** — a defense-in-depth layer on top of the first two, valuable specifically for the free-text chat body where minimization can't remove PII the student chooses to type, but never treated as sufficient on its own.

## Opinionated recommendation for VisionQuest (Node/TS, 100–500 students)

**Order of operations, roughly in effort/impact order:**

1. **First (days, not weeks): put a Data Processing / Zero-Data-Retention contract in place with a hosted open-weight provider** (Groq, Fireworks, Together, or Cerebras — whichever best matches the model family already validated in the local bake-off work this repo has done) and add it as a new `AiRole`-routable provider in the existing `src/lib/ai/provider.ts` abstraction, exactly the same shape as the Gemini/Ollama split already there. This alone gets VisionQuest "fast cloud LLM without exposing PII to a training pipeline," is nearly free to implement given the existing role-routing architecture, and is the single highest-leverage move on this whole list. **This does not, on its own, satisfy `student_record`-must-be-local per the current FERPA policy in `.claude/rules/sage-ai.md`** — that policy would need an explicit, documented update (an owner decision, same class as the existing "USER — FERPA ruling needed" open item) to say a ZDR-contracted hosted provider satisfies the local-only requirement, or this option only helps the non-`student_record` traffic.
2. **Second (a few days): the Postgres RLS identity/behavioral split.** Given `Student` already centralizes the five direct identifiers, this is schema/role discipline, not new infrastructure: a stricter role or policy gating direct read of `name/email/phone/address/dateOfBirth`, plus a lint rule (matching the existing `no-restricted-syntax` pattern already used for log-PII and student-alert-visibility) that forbids interpolating those raw fields into any prompt-builder function. Cheap, durable, and closes the "structural" identifiers with near-zero false-negative risk (it's not NER-dependent — it's a type-level guarantee).
3. **Third (1–2 weeks): structured substitution for chat free text.** Build the request-time substitution using the DB-known identifiers deterministically (word-boundary + possessive-aware matching, learning directly from VisionQuest's own `explain_job` substring-matching bug-fix pattern), and layer a light in-process NER pass (GLiNER-PII via `onnxruntime-node`, quantized small/edge checkpoint) for identifiers the DB doesn't know about (family members, employers, other people's phone numbers mentioned in chat). Ship this **red-baselined against an adversarial fixture built the same way this repo already builds its crisis-detection fixtures** — nicknames, lowercase, misspellings, WV-regional names — before trusting it, because every vendor and open-source option surveyed here has a documented, unsolved gap on exactly that text shape. Use typed, grammatically-plausible placeholders (not bracketed tokens) given the published evidence that bare `[REDACTED]`-style tokens measurably degrade model reasoning quality. Add tool-call arguments as a second redaction checkpoint (the existing `SageOperation` ledger/confirm-card infrastructure is the natural place to also verify no raw identifier survived into a tool argument).
4. **Fourth, in parallel, independent of the redaction question: move the local model off the home Mac onto a dedicated cloud GPU VM (L4-class).** This fixes the reliability problems this repo has already extensively documented (keep-alive/model-eviction, contention between models, the unmeasured/likely-wrong 9-minute p50 projection) regardless of whether steps 1–3 ship, and is cheap enough ($0.39+/hr) that it should be evaluated even as a pure ops improvement to today's local-Ollama setup.
5. **Do not build or buy a full third-party data-privacy-vault product (Skyflow etc.) at this scale.** The 100–500-student, single-tenant, already-RLS'd Postgres app gets most of the same security property from step 2 at a fraction of the cost and integration complexity; revisit only if VisionQuest's compliance posture needs vendor-attested SOC2/HIPAA-grade controls beyond what internal RLS discipline provides.
6. **Formalize the contract as policy, not just an engineering artifact**: have the ZDR agreement, the minimization decisions (which `AiTask`s actually need real identifiers), and the redaction methodology written up together as VisionQuest's answer to the ED PTAC "defensible methodology" requirement — this is a cheap addition to `docs/DATA_RETENTION_POLICY.md` / the FERPA rule file, and is exactly what the legal literature says redaction alone does not provide.

**Estimated total effort**: steps 1–2 are days each; step 3 is the real engineering lift (1–2 weeks including the adversarial fixture and tool-call-argument checkpoint); step 4 is ops work that can run in parallel; step 6 is a documentation/policy pass. None of this requires "inventing something new" in the sense of novel research — it's an assembly of published, production patterns, which is itself useful to tell the owner: the pieces exist, the job is integration + a written policy + a rigorous internal eval, not invention.

## Candid "what will still leak" list

Even after implementing everything above:

- **Anything the student types that the NER layer misses.** Every vendor and open-source detector surveyed has a documented, unresolved gap on nicknames, lowercase text, and misspellings — exactly WV colloquial chat. This is not a solvable-to-zero problem; it needs an ongoing adversarial-eval discipline (same as VisionQuest's crisis-detection work) and an accepted residual-risk number, not a claim of full coverage.
- **Quasi-identifiers that individually look harmless.** A specific employer name + a specific small-town location + a specific certification track + an age range is very plausibly enough to re-identify someone in a population this small, even with primary identifiers (name/email/phone/DOB) fully redacted — this is the NIST SP 800-188 disclosure-risk point, and no redaction tool addresses it, because none of those fields is itself "PII" in the narrow sense a detector looks for.
- **Session/conversational context accumulation.** A single turn might be safely de-identified, but a multi-turn conversation where the student mentions their town in turn 3, their employer in turn 7, and their child's school in turn 12 can be re-identifying in aggregate even if each individual turn passed a per-turn redaction check — per-turn redaction does not compose into per-conversation safety without deliberate design (e.g., tracking already-revealed quasi-identifiers across the session).
- **Tool-call arguments and any place the model reconstructs an identifier from context it still has**, as documented in section 2 — a redaction layer applied only to the visible chat text is not applied to structured tool arguments unless explicitly wired to be.
- **Observability/tracing/logging infrastructure** — any LLM-ops tracing tool (LangSmith-style) that captures full request/response pairs by default will re-introduce everything the redaction layer removed unless it's explicitly configured to receive only the post-redaction text, or masked itself. VisionQuest's own `no-restricted-syntax` log-PII lint rule is the right pattern to extend to any future observability tooling.
- **The provider's own infrastructure logs, even under a ZDR contract**, in the narrow window before the "zero retention" policy actually purges the request (transient processing logs, abuse-monitoring exceptions some contracts carve out) — a contract reduces this risk to a legal/reputational one rather than eliminating the technical fact that the plaintext transits the vendor's infrastructure at least momentarily. Confidential computing (option 4b) is the only approach in this survey that removes even that momentary exposure, at real cost/complexity.
- **Fine-tuning risk is a non-issue here** (VisionQuest is not fine-tuning on this data), but is worth naming as the sharpest form of this problem in the literature: PII that ever enters a model's weights cannot be selectively "un-trained," which is why the ZDR-and-no-training contractual language matters as much as the technical redaction — a provider that trains on inputs by default is a different and worse risk than one that merely logs transiently.
