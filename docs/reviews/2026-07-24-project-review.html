VisionQuest is a well-engineered system running without a steering wheel.

The code is materially more mature than the project's own documentation admits — the security core, the Sage agent's confirmation boundary, and the July verification work are genuinely above grade for a solo alpha. What has failed is the operating loop around it: the 90-day charter lapsed 33 days ago with no successor, the headline outcomes were never measurable, and a recurring pattern has set in where safety-critical policy degrades silently to the permissive side whenever a config row or a CI secret is missing. The build quality is not the risk. The absence of a current definition of "done" is.

What is broken, grouped by why

Weaknesses

Clustered by failure pattern rather than by subsystem, because the patterns repeat across subsystems and the pattern is the thing worth fixing. Severity grades are provisional except where marked verified.

Pattern one — safety policy that degrades quietly to the permissive side

The most consequential cluster. In each case the safe behavior is documented as enforced, and the code does the less safe thing when something is merely absent.

Criticalcrisis-safety

The crisis scan and staff alert run only after a fully successful model stream

Both the 988 resource injection and the staff wellbeing alert sit inside the success path of the streaming response. If the local provider is down and the route returns 503, if the model errors mid-stream, or if the student closes the tab, a message containing explicit suicidal intent is saved to the database and no alert is ever raised — the deterministic detector never runs. The failure modes that suppress the alert are exactly the ones most likely to co-occur with a student in distress retrying a broken app.

FixRun the detector on the user's message and fire the alert immediately after that message is saved, before provider resolution. The detector is pure and synchronous, so this costs nothing; keep the reply-side resource block where it is.

Highsage-chat

The FERPA "local-only" guarantee is not what the code enforces

Both CLAUDE.md and the Sage rules state that student-record and staff-entered prompts are local-only by FERPA policy. The resolver routes those sensitivities to the local provider only when a system config row explicitly says local — and an unset row defaults to cloud. So a fresh environment, a wiped config, or a mis-set value silently sends student-record content to Gemini while the documentation claims it cannot happen. Embedding routing shares the same fail-open default.

FixPick one truth and make the code the authority. Either fail closed for those sensitivities — 503 when no local provider, with an explicit owner-acknowledged cloud override flag — or rewrite both docs to describe cloud-by-default with consent as the basis.
