## Architecture Notes
- Auth: JWT in httpOnly cookies (SameSite=strict), scrypt password hashing (legacy PBKDF2 rehashed on login), TOTP MFA, `sessionVersion` invalidation
- AI providers: `src/lib/ai/` abstraction — Gemini (cloud) + Ollama (local), routed by data sensitivity (`resolveAiProvider`; student_record/staff_entered are local-only per FERPA policy); explicit safetySettings; transient-failure retry pre-first-token; prompt revisions stamped via `SAGE_PROMPT_REVISION`
- Chat: SSE streaming from `/api/chat/send` (heartbeats, disconnect handling), two-call pattern (conversation + prioritized async extraction in `src/lib/chat/post-response.ts`); token-budget-aware history trimming
- RAG: live hybrid pgvector + FTS retrieval with RRF (`src/lib/sage/hybrid-retrieval.ts`), `ProgramDocument` corpus + `catalog/` OKF layer, gating red-team/guardrail evals in CI (`.github/workflows/sage-evals.yml`)
- Safety: deterministic crisis detection (English + Spanish) with 988 safety net, structured crisis context cards to assigned instructors, failed extractions dead-lettered for teacher review
- Verification layer: orientation instructor-led steps, Sage-proposed goals, and certifications require human confirmation (intervention-queue-driven); staff reads of student data are audited
- File storage: local `./uploads/` in dev, Supabase Storage (S3-compatible) in prod
- CSRF: Origin header validation middleware for all POST/PUT/PATCH/DELETE to /api/*; Postgres RLS with spoofable-header stripping in `src/proxy.ts`
- Student routes: `(student)` route group, Teacher routes: `(teacher)` route group
- Data lifecycle: retention policy in `docs/DATA_RETENTION_POLICY.md` (durations pending OWNER-CONFIRM), admin-only offboarding with export-before-deactivate
- Sage agent: `src/lib/sage/agent/` — registry, executor (role-gated), HMAC confirm cards (`confirmation.ts`), write tools, career tools; every write ledgered in SageOperation + AuditLog
- Memory: `src/lib/sage/memory/` — RLS student-scoped, fire-and-forget extraction, weekly pg_cron consolidation
- Retrieval: hybrid pgvector+FTS RRF (`sage_hybrid_search` SQL fn); eval harnesses: `sage:rag:harness`, `sage:memory:eval`, `sage:agent:eval`
- Evals are hard gates — run all three before merging Sage-affecting changes

## Known Issues
- ~~**MemPalace and CodeGraph are documented as available but are not wired**~~ — Superseded: both are wired on the Mac (MemPalace 2026-07-27, CodeGraph 2026-07-28) and MemPalace is backfilled (394k drawers as of 2026-08-19). Auto-memory holds the detail (`auto-memory-has-no-backup`).
- **A tool call the caller never offered comes back as an empty reply, not an error** (verified 2026-07-27, Ollama 0.32.4). gemma4's model template is `{{ .Prompt }}`, so Ollama uses a **built-in Go renderer/parser** for the family. When the model emits its native `call:<tool>(args)` syntax, that parser strips it out of `message.content`; if the request declared no `tools`, there is nowhere to put it and the reply is `{"role":"assistant","content":""}` on native `/api/chat` — no `tool_calls`, no error, `done_reason: "stop"`. Any prompt that advertises tools to a no-tools call can hit this. Diagnose with `/api/generate` `raw: true` (bypasses renderer AND parser, shows literal tokens); `/v1/chat/completions` is the next best surface because it exposes `finish_reason: "tool_calls"` and a `reasoning` channel that native hides. Declaring the exact tool name makes the same output parse cleanly, so this is an undeclared-tool drop, not a broken parser. `OllamaProvider.generateResponse` currently passes the `""` straight through — see Open Items for the follow-up (#147 has merged, so it now targets `main`).
- ~~**Thinking models return empty replies through `OllamaProvider`**~~ — Fixed by PR #147 (2026-07-27): reasoning is now disabled by default and a truncated turn with no visible content throws instead of returning `""`. The durable gotcha survives the fix: **Ollama's two API surfaces take different reasoning knobs and each silently ignores the other's** — `/v1/chat/completions` honors only `reasoning_effort:"none"` (and reports reasoning as `message.reasoning`), `/api/chat` honors only `think:false` (reporting `message.thinking`). `postChat` tries `/v1` first and real Ollama answers it, so the live path is OpenAI-compat; a native-only change looks correct and does nothing. Re-enable reasoning with `ai_provider_reasoning` and size it with `ai_provider_max_output_tokens`. Harness auto-memory holds the detail (`thinking-models-return-empty-via-ollama-provider`)
- **A worktree without its own `node_modules` silently borrows the main checkout's — including its generated Prisma client** (hit 2026-07-27). Node resolution walks up to `projects/VisionQuest/node_modules`, so a worktree on `main` can be running a client generated from whatever branch the main checkout happens to sit on. Symptom: `prisma.<model>` is `undefined` and you get `Cannot read properties of undefined (reading 'upsert')` — the model exists in your schema but not in the borrowed client. **Do not "fix" this with `npx prisma generate` from the worktree**: that rewrites the shared client from your schema and strips models the other branch needs (on 2026-07-27 it would have removed `CareerAssessmentSnapshot`, which only exists on `feature/apify-job-sources`, breaking that in-flight work). Run `npm ci` inside the worktree instead, then generate — verify isolation afterwards by grepping the main checkout's `node_modules/.prisma/client/index.d.ts` for the other branch's models. The same missing-`node_modules` root cause also makes `src/lib/spokes/forms-delivery.test.ts` fail with "tsx CLI not found in node_modules"; that one is a harmless artifact, and CI passes it
- **Reasoning-off (the PR #147 default) makes `info-certs` flaky on gemma4:latest** — accepted trade, not a blocker (owner call, 2026-07-27). Four draws each, real provider + real harness prompt, models evicted between arms: reasoning ON → 555/365/614/560 chars (4/4 answered); reasoning OFF → 0/0/242/63 (2/4 empty). Mechanism: under agent mode the scenario needs the model to notice #143's `PROGRAM DOCUMENT REFERENCE` block and override the "call `lookup_program_info` first" rule, and the reasoning channel appears to be doing that judgment. Net across models: `gemma4:26b-a4b-it-qat` 0/8 → 7/8, `gemma4:latest` 8/8 → 7/8. **Resolved 2026-07-27**: reasoning ON with a raised budget does *not* beat it — on the 26b model that setting scored 1/8 in 2223s (7 of 8 calls exceeded the 300s cap) against 7/8 in 159s for the shipped default. There is no globally better setting, so treat `ai_provider_reasoning` as a **per-deployment** choice: leave it off wherever a large thinking model is configured (it is otherwise unusable), and turn it on for a smaller model like `gemma4:latest` if grounded-Q&A reliability matters more than the flakiness above

This produced a confidently wrong conclusion on 2026-07-27 before eviction reversed it. Evict with `curl -s localhost:11434/api/chat -d '{"model":"<m>","messages":[],"keep_alive":0}'`; check with `/api/ps`.
